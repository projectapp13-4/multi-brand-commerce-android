# P3-00 Data Ownership and Persistence

Date: 2026-08-10

Status: **ACCEPTED P3-00 DATA CONTRACT — P3-03 HISTORY AND P3-05 WISHLIST IMPLEMENTED**

This document finalizes source-of-truth, persistence, clearing, migration, backup and cross-device behavior for Phase 3. It preserves the proven Phase 2 Keystore boundaries. P3-03 introduced device-local Room search history and P3-05 extends the same database with the approved local-only wishlist; neither slice introduces a backend, remote wishlist sync, telemetry, or new production configuration.

## Room schema and migration decision

P3-00 approves Room only for search history and local wishlist. P3-03 established `gurbakir-local.db` at schema version 1 with the exported schema checked in under `app/schemas`; P3-05 advances it to version 2. The stable `search_history` and `search_history_settings` tables use environment/market partition keys; normalized query is part of the history primary key. The new `wishlist` table uses environment/market/full-product-GID as its primary key and stores only its added timestamp. Version 1 has no predecessor migration; version 2 has an explicit `1 -> 2` migration. Every later database version must provide and test a forward migration from every then-supported version.

- Search history entity intent: normalized query key, display query, last-used timestamp, environment and market partition. Enforce maximum 10 after write and 30-day expiry on read/maintenance.
- Wishlist entity intent: stable product identity, added timestamp, environment and market partition. Do not persist mutable title/price/inventory as truth; rehydrate from Storefront.
- P3-05 extends this shared database by adding the wishlist schema in version 2 with an explicit `1 -> 2` forward migration that leaves both history tables and their rows intact. Exported versions 1 and 2 are retained. A separately named wishlist database was not introduced.
- `fallbackToDestructiveMigration` is prohibited for retained wishlist data and is not a default for history. An approved corruption recovery may clear only a rebuildable/correctly disclosed data class after evidence and user-safe handling.
- OAuth/session and cart capability material never migrates into Room or plaintext DataStore.

P3-03/P3-05 use no destructive or downgrade fallback. A Room/SQLite open or operation failure fails closed for the process: history or wishlist storage is shown unavailable, no local record is changed, and remote discovery remains usable. User wishlist add/remove is idempotent; clear-all requires an explicit confirmation. Wishlist rehydration failure retains the identity, labels the row, and permits local removal without network access. Search remove/clear/disable remains immediate; disable is stored and clears the active partition in the same Room transaction. Expiry maintenance runs on history read/write, and overflow trimming runs after history write. Development/staging and Turkey-market keys cannot cross-display even though current application IDs already separate environments.

## Cart ownership, restoration and visibility

### State authority

- `Anonymous`: valid cart with no customer buyer identity association.
- `CustomerAssociated`: valid cart whose association matches the current valid customer session and market context.
- `DetachPending`: logout/terminal expiry requested; buyer-identity removal has not yet been confirmed.
- `Quarantined`: association cannot be proven safe. Lines/cart capability are not exposed as anonymous and checkout is prohibited.

### Policy

1. Restore local protected cart reference, then read authoritative remote cart before presenting mutable state.
2. Definitive invalid/expired remote result clears the protected reference. Transport/GraphQL/transient failures retain the last valid reference/state.
3. Login with a guest cart performs one explicit reconciliation/association operation. Ambiguous outcome is re-read before retry; never duplicate lines by blind replay.
4. Logout/expiry first protects/clears the customer session according to the session coordinator, then attempts cart detachment. Only confirmed detachment yields `Anonymous`; failure yields `DetachPending`/`Quarantined`.
5. Buyer identity affects market/pricing and authenticated checkout. A UI sign-in flag cannot substitute for Shopify association evidence.
6. Quantity must be positive and bounded in UI; existing gateway accepts at most 250 line mutations per request and remains subject to Shopify server validation/normalization. P3-06 chooses user-facing per-line controls from merchant/server policy rather than inventing a stock limit.
7. Cart notes are absent in Phase 3. Cart attributes/free text are not introduced by inference.
8. Checkout refreshes the eligible cart. Genuine completion clears only that cart; cancel/decline/failure retains it. Process death never implies completion.
9. Any Phase 2 synthetic proof cart is not adopted into production UX. No opaque ID is guessed; normal remote expiry applies to any unreachable historical cart.

P3-06 implements this policy in `CartCoordinator` and the versioned `AndroidKeystoreCartSessionStore` envelope. A complete opaque cart ID, expiry, and ownership are encrypted together; UI state receives only redacted line/totals presentation. `Anonymous` remote restoration verifies that Shopify reports no associated customer before lines are exposed. `CustomerAssociated`, `DetachPending`, and `Quarantined` records are not exposed through ordinary anonymous restoration. Detachment writes `DetachPending` before the remote operation; only a confirmed no-customer response becomes `Anonymous`, while ambiguous transport state remains pending and non-retryable/unverifiable state becomes quarantined. Mutations are serialized, and ambiguous add/update/remove outcomes are re-read before any retry so lines are never blindly replayed.

## Backup, reinstall and migration baseline

The current app disables backup/data extraction for protected app data. P3-00 retains that baseline. Reinstall therefore clears customer session, cart reference, Room history/wishlist and app preferences unless Android platform-owned per-app language behavior restores a setting. The UI must not promise wishlist/history persistence across uninstall or devices.

Changing backup policy is a privacy/product/security decision requiring a data-class inventory, encryption, cross-device semantics, deletion behavior, restore/version tests and updated disclosure. It cannot be changed incidentally by a feature slice.

## Backend and account-deletion boundary

No project backend exists. Device-local wishlist, search history and cart/session orchestration do not justify one. If account deletion or another accepted feature cannot be satisfied by Shopify/current owned resources, a separate approved ADR and threat model must define capability, data owner, authentication/authorization, validation, secrets, storage, retention/deletion, abuse controls, logging/monitoring, availability, operations and rollback before code or deployment.

The reference Worker proves only client-visible route use. Its source, authorization, persistence, merge, conflict, retention, deletion, logging and operational behavior remain `UNKNOWN` and are not inputs to this data model.
